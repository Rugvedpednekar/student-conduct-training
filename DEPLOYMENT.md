# Free deployment: Render + Neon

This repository contains a FastAPI/Jinja2 server and a persistent SQLAlchemy database; GitHub Pages cannot serve the backend.

## Security first
- The old repository history includes bootstrap passwords. Treat them as compromised, rotate any accounts that have ever used them, and **never reuse them**. Removing them from the current file does not erase Git history.
- Do not upload actual student information, conduct cases, Maxient exports, or other institutional records to an unapproved public demo. Obtain institutional approval and a security/privacy review before real use.
- A free tier is suitable for a demo, not an approved production student-records system.
- The `INITIAL_*_PASSWORD` values are applied **only to missing accounts**; changing env vars will not reset passwords for existing accounts. Use a controlled password-reset procedure or a fresh database for a demo.
- The optional AI chat can incur charges and must not receive sensitive data without approval.

## 1. Create a Neon PostgreSQL database
1. Sign in at https://console.neon.tech and create a free project.
2. Copy the database connection URL including SSL requirements. Keep it secret.
3. No database credentials should be committed to the repository.

## 2. Deploy the Render Blueprint
1. Open https://dashboard.render.com, select **New > Blueprint**, and connect this repository.
2. Select the deployment branch after merging the reviewed pull request, or use the branch for testing only.
3. Render reads `render.yaml` and creates a free Python web service.
4. In Render's environment variables, supply:
   - `DATABASE_URL`: the Neon connection string.
   - `INITIAL_ADMIN_USERNAME`: a new demo admin username.
   - `INITIAL_ADMIN_PASSWORD`: a unique random password of at least 12 characters.
   - Optionally `INITIAL_USER_USERNAME` and `INITIAL_USER_PASSWORD` (both or neither).
   - `SECRET_KEY` is automatically generated by the Blueprint; never use a known/default key.
   - `SECURE_COOKIES=true` is configured by the Blueprint.
5. Check the build logs for errors and open `/healthz`. The app creates tables and seeds content and optional initial accounts during startup.
6. Verify `/login`, `/dashboard`, admin authorization, saved content after restart, and that cookies are secure on HTTPS.

**Alternative manual Render Web Service setup:** Build: `pip install -r requirements.txt`; Start: `uvicorn app.main:app --host 0.0.0.0 --port $PORT`; health check `/healthz`. Manually set all environment variables including a 32+ character random `SECRET_KEY`.

## Local development
```bash
python -m venv .venv
# Activate venv for your shell
pip install -r requirements.txt
cp .env.example .env
# Fill SECRET_KEY (32+ random characters) and INITIAL_ADMIN_* in .env
uvicorn app.main:app --reload
```

For a strong session key run `python -c "import secrets; print(secrets.token_urlsafe(48))"`.

## Database and persistence
- PostgreSQL on Neon is persistent even when Render's free web instance sleeps.
- The default SQLite database is for local development only; Render free filesystem is ephemeral. Do **not** use SQLite on Render for persistent data.
- The application currently creates missing tables with SQLAlchemy on startup. For schema upgrades, review Alembic migration compatibility before relying on it in production.
- Render's free instances sleep and can cold start; plan limits and availability can change.

## Known limitations
- This change secures account bootstrap and session key defaults, but does **not** constitute a full application security audit. Before real student data, review access control, file processing, CSRF, rate limiting, session management, secret rotation, data retention, and institutional compliance.
- The overdue-sanctions generated files are temporarily written to Render's ephemeral filesystem and disappear on restart.
- AI chat requires a separately configured API credential and may not be free.
